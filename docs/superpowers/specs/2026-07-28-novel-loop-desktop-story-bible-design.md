# Novel Loop Desktop Story Bible Integration Design

Date: 2026-07-28

## Goal

Connect the existing Novel Loop `buildBible` engine capability to the secure
Electron desktop application as the first author-facing generation workflow.
An author can start Story Bible generation from Project Overview, understand
the current stage, stop safely between stages, recover from failure, and review
the four generated foundation documents.

The renderer must never receive a project filesystem path, execute Codex, or
write project files directly.

## Scope

This milestone includes:

- Start Story Bible generation from Project Overview.
- Use the local `codex-text` provider through the existing engine boundary.
- Run generation as a main-process background task.
- Report author-facing progress for all four foundation documents.
- Allow a stop request that takes effect after the current Codex call.
- Preserve partial artifacts and run provenance after failure or cancellation.
- Retry an incomplete generation safely from Project Overview.
- Refresh Project Overview after completion.
- Present a read-only foundation review for:
  - Story Bible
  - Genre Contract
  - Reader Promise
  - Style Guide
- Keep Story State and chapter queue unchanged.

## Non-goals

- Editing or approving Story Bible documents.
- Global outline generation.
- Chapter planning or drafting.
- Overwriting an already complete Story Bible.
- Multiple providers or provider selection in the renderer.
- Direct renderer access to paths, Codex commands, tokens, JSONL, or run IDs.
- Full cross-restart task resumption.

## Author Flow

```text
Project Overview
-> Prepare Story Foundation
-> Confirm local Codex generation
-> Background generation progress
-> Review generated foundation
-> Return to refreshed Project Overview
```

The confirmation explains that generation may take several minutes, writes
draft foundation documents only, and does not change the formal Story State.

## Completion Rule

Story Bible is available only when all four strategy artifacts exist:

- `strategy/story_bible.md`
- `strategy/genre_contract.md`
- `strategy/reader_promise.md`
- `strategy/style_guide.md`

A single partial artifact must not mark the foundation as ready.

## Background Task Model

The Electron main process owns one active foundation task per project.
Renderer calls use opaque `projectKey` and `taskId` values.

Task statuses:

- `queued`
- `running`
- `stop_requested`
- `succeeded`
- `failed`
- `cancelled`

Task stages:

- `preparing`
- `story_bible`
- `genre_contract`
- `reader_promise`
- `style_guide`
- `finalizing`
- `completed`

The renderer polls task status through the typed preload API. Polling does not
read the filesystem or invoke Codex.

The stop action is cooperative. It records `stop_requested` immediately and
prevents the next strategy prompt from starting. It does not terminate an
in-flight Codex process. The UI states this as "finish the current step, then
stop."

## Retry And Existing Artifacts

An already complete foundation is never regenerated by this workflow.

When a previous run failed or was cancelled after writing only part of the
foundation, retry starts a new provenance run and regenerates the incomplete
foundation set. Existing partial strategy artifacts may be replaced only by
this internal recovery path. The user is not given a generic force-overwrite
control.

## Engine Boundary

The root package adds a desktop-specific Story Bible function that:

- accepts a canonical project root;
- derives `projectsRoot` and `projectId` locally;
- invokes `buildBible` with provider `codex-text`;
- resolves packaged prompt and output-schema assets independently of process
  working directory;
- emits stage progress;
- checks a cooperative stop callback between prompt calls;
- returns only run outcome and artifact metadata to Electron main.

The desktop main process wraps this function behind a gateway so tests can use
a deterministic fake without a real Codex installation.

## Typed Desktop API

The preload API adds a narrow `foundation` namespace:

```ts
foundation.start({ projectKey }): Promise<FoundationTask>
foundation.get({ taskId }): Promise<FoundationTask>
foundation.cancel({ taskId }): Promise<FoundationTask>
foundation.read({ projectKey }): Promise<FoundationReviewResult>
```

Every request and response is validated with Zod in main. The renderer receives
document content, author-facing status, and stable opaque identifiers only.

## UI

Project Overview changes:

- Incomplete foundation: enabled `Prepare Story Foundation` action.
- Active task: stage list, current stage, elapsed state, and stop action.
- Failure: natural-language reason plus retry action.
- Cancelled: partial work explanation plus retry action.
- Complete: `Review Story Foundation` action and refreshed readiness status.

Foundation Review is a reading surface, not a dashboard:

- compact project header and return action;
- document navigation for the four foundation sections;
- one centered long-form reading column;
- generated-draft status;
- no raw paths, run IDs, schema names, or Codex JSONL.

## Error Handling

Main maps internal failures to author-facing categories:

- Codex unavailable
- Codex login required
- Usage limit reached
- Generation timed out
- Invalid generated output
- Project data changed or unavailable
- Unexpected generation failure

Technical codes remain available only in main-process logs and run provenance.

## Security And State Protection

- Renderer remains sandboxed with no Node integration.
- Main validates trusted IPC sender and all payloads.
- Provider is fixed to `codex-text`; renderer cannot inject a binary or CLI
  argument.
- Codex keeps the existing read-only sandbox boundary.
- Story State and chapter queue hashes are captured before and after tests and
  must remain identical.
- No snapshot, canon patch, state diff, or commit report is created.
- Auth files and tokens are never read or returned.

## Testing

Tests cover:

- Contract schema acceptance and rejection.
- Trusted IPC validation for all foundation channels.
- Preload exposes only the narrow foundation methods.
- One active task per project and task lookup isolation.
- Ordered stage progress.
- Cooperative stop between stages.
- Retry after partial failure.
- Complete foundation cannot be overwritten.
- Four-document completion rule.
- Foundation review rendering and keyboard behavior.
- Natural-language failure states.
- Story State and queue remain unchanged.
- Existing root and desktop suites remain green.
- Required real Electron security smoke remains green.

## Acceptance

From a newly created desktop project with Codex ready:

1. The overview offers Story Foundation generation.
2. Starting generation shows meaningful staged progress.
3. Completion produces all four strategy documents and refreshes the overview.
4. The author can open and read every generated document.
5. Cancellation or failure leaves the project recoverable.
6. No Story State or chapter queue mutation occurs.
7. No filesystem path or internal provider detail reaches the normal UI.
